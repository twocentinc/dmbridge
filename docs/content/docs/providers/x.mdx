---
title: X
description: Prepare an X app and connect a personal XChat account.
---

Create and configure an OAuth 2.0 app using X's
[developer app guide](https://docs.x.com/fundamentals/developer-apps). Add the
exact callback URL you plan to use. For local setup, X recommends
`http://127.0.0.1` rather than `localhost`.

## What you need

| Value | Required? | What to enter |
| --- | --- | --- |
| Account name | Yes | A local dmbridge label for this login. The setup script defaults to `personal`. |
| OAuth client ID (`clientID`) | Yes | The client ID from your X app's OAuth 2.0 settings. |
| Client type (`clientType`) | Yes | `public` for a native/local app using PKCE, or `confidential` for a client that can safely hold a secret. The script defaults to `public`. |
| OAuth client secret (`clientSecret`) | Confidential clients only | The client secret from your X app. Public clients must leave this empty. |
| Redirect URI (`redirectURI`) | Yes | An absolute callback URL registered exactly the same way in your X app. The script defaults to `http://127.0.0.1/callback`. |
| OAuth callback URL (`callbackURL`) | Yes, after approval | The complete URL X redirects you to. Paste it back into the setup script; dmbridge extracts the authorization code and state. |
| XChat passcode | Only for passcode-protected XChat access | Your XChat passcode. It is entered as a secret after OAuth and is never passed as a command-line argument. |

dmbridge requests `dm.read`, `dm.write`, `tweet.read`, `users.read`,
`media.write`, and `offline.access` automatically. You do not need to create or
paste access tokens, refresh tokens, PKCE values, an authorization code, or an
OAuth state value yourself.

`realmTokenIssuerURL` is an optional advanced override for a custom XChat realm
token issuer. The guided setup does not ask for it, and normal X accounts do
not need it.

From a dmbridge repository checkout:

```sh
./scripts/connect-x.sh
```

The script asks for the values above one line at a time. It prints the OAuth
link, waits for the callback URL, optionally stores the XChat passcode, and
finishes with a live read-only check.

If XChat rejects the passcode, dmbridge immediately forgets it rather than
risking repeated failed attempts.

The script is safe to rerun. Replacing an existing authorization requires
explicit confirmation. Set `DMBRIDGE_BIN` when the executable is not named
`dmbridge` or is not on `PATH`:

```sh
DMBRIDGE_BIN=/absolute/path/to/dmbridge ./scripts/connect-x.sh
```

## Externally managed OAuth credentials

By default, dmbridge owns the X OAuth refresh lifecycle and atomically stores
rotated access and refresh tokens. Use external refresh mode only when one
trusted local integration is the sole OAuth writer and dmbridge is only a
credential consumer.

The external writer must provide a complete X credential with
`refreshMode: "external"`. Inspect the current request contract instead of
guessing fields:

```sh
dmbridge x doctor --schema accounts.import.x.request --no-input
```

Validate a prepared credential without storing it, then import it:

```sh
dmbridge accounts import x --account personal --request credential.json \
  --dry-run --no-input
dmbridge accounts import x --account personal --request credential.json \
  --yes --no-input
```

Use `--request -` to read JSON from stdin. Never place tokens in command-line
arguments, logs, or prompts, and never hand-edit `credentials.json`.

For an externally managed account, dmbridge never exchanges the refresh token.
The external writer must atomically import the complete credential after every
authorization or refresh. Normal commands fail with
`auth.externalCredentialUpdateRequired` when the imported access token is
expired or within the refresh safety window. Do not let two processes refresh
the same token chain.
